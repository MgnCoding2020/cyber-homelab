# Lab 04 — Active Directory

> **Status:** In progress
> **Where:** VM — Windows Server 2022 Evaluation (`lab-dc-01`), all changes inside the Hyper-V guest

## Problem

Local, per-machine accounts (SAM-based) don't scale: every workstation has its own user database,
password policy, and audit trail, so there's no single point to enforce identification/authentication
requirements or account lifecycle controls across a fleet. Active Directory Domain Services (AD DS)
centralizes identity into one forest/domain so accounts, group membership, and policy can be managed
and audited from one place.

## What I did

- **Phase 1 — network config:** Renamed the fresh Server 2022 Evaluation VM to `lab-dc-01` and
  assigned it a static IP/gateway so it can reliably serve AD DS/DNS.
- **Phase 2 — AD DS role + forest promotion:** Installed the AD Domain Services role and ran
  `Install-ADDSForest` to promote `lab-dc-01` into the first domain controller of a new forest,
  `corp.lab` (NetBIOS `CORP`), with DNS installed alongside.
- **Phase 3 — post-promotion verification:** Confirmed the forest and domain came up correctly with
  `Get-ADDomain` / `Get-ADForest` after the automatic post-promotion reboot.

**Next (Phase 4, not yet started):** create an OU structure, join a client VM to `corp.lab`, and push
a GPO — this is where the AU-2 and account-lifecycle controls below actually get enforced rather than
just made possible.

**Sanitization note:** transcripts capture everything typed and displayed, including full command
output. Before committing, review each transcript for anything that shouldn't be public: real
passwords (never type one directly into a command that gets logged — use `Get-Credential` or
`Read-Host -AsSecureString` instead), and mask any internal IPs or pre-rename autogenerated hostnames
(e.g. the Windows-assigned `WIN-XXXXXXXXXXX` name a fresh VM has before `Rename-Computer` runs)
consistent with the rest of the repo.

**Evidence workflow — pulling transcripts from VM to host:** each phase starts with
`Start-Transcript -Path "C:\Evidence\<file>.txt"` run inside the VM. Once a phase is done, pull the
file to the host repo via PowerShell Direct, from an **elevated PowerShell window on the host**:

```powershell
$cred = Get-Credential   # CORP\Administrator once the VM is domain-promoted

Invoke-Command -VMName "lab-dc-01" -Credential $cred -ScriptBlock {
    Get-Content 'C:\Evidence\<file>.txt' -Raw
} | Out-File "C:\Users\Michael\Documents\cyber-homelab\03-active-directory\transcripts\<file>.txt"
```

Two gotchas hit during Phase 2/3:
- **Use the full absolute destination path**, not a relative one — an elevated PowerShell window
  defaults to `C:\Windows\System32`, so a relative `Out-File` path resolves there and fails with
  `DirectoryNotFoundException`.
- **Credential changes after promotion.** Before `Install-ADDSForest` runs, authenticate as the local
  `Administrator`. Once the VM is promoted, local SAM accounts stop working for logon — PowerShell
  Direct needs `CORP\Administrator` instead. For the first DC in a new forest, that domain account
  keeps the same password the local `Administrator` account had (this is separate from the DSRM
  password, which is only used for DSRM boot recovery).

## What I learned

Promoting the first DC in a new forest isn't just a role install — it silently converts the box's
identity model: the local `Administrator` account that worked for PowerShell Direct pre-promotion
stops authenticating post-promotion, and `CORP\Administrator` (same password, different account) takes
over. That distinction — a real behavior of `Install-ADDSForest`, not a guess — was the main
troubleshooting moment of this phase and is worth remembering before Phase 4's client domain-join.
